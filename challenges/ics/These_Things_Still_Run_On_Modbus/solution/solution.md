# These Things Still Run On Modbus

**Category:** ICS
**Difficulty:** Medium
**Author:** Voyager 1

## Description (what the competitor will see)

AstraTech Industries runs a fleet of autonomous DM-7 mining drones out in
the belt. One of them is exposed on the network at
`<challenge-host>:502` — full Modbus/TCP telemetry and control, no
authentication.

Figure out what you're actually talking to, find its documentation, and
work out how to authorize its emergency destruct protocol.

## Files Provided

- None — connect directly to the Modbus/TCP service. Everything else
  needed to solve this is discoverable in-band.

## Flag

`flag{d3t0n4t3_dm7}`

## Solution

1. Player connects to the drone (`drone` service, 10.13.37.30:502).
2. Player sends FC43 (Read Device Identification), which reveals vendor
   name (AstraTech Industries), product code (DM-7), and a vendor URL
   (`http://10.13.37.50`).
3. That URL is the `website` service — an in-universe AstraTech
   marketing site. Player navigates Support → manuals → DM-7 Operations
   Manual v2.3 (a PDF, generated by `src/website/generate_pdf.py`).
4. Section 9 of the manual ("Emergency Protocols") documents the
   emergency destruct protocol (EDP): write `0x4444` to holding register
   `1337` (unit ID `0x0A`) to arm it.
5. After that write, holding registers `2000`-`2017` contain the flag,
   one ASCII character per register — player reads them back to recover
   the flag.

## Solve Script

See `solution/solve.py` — walks all four steps end-to-end:

```bash
cd solution
pip install -r requirements.txt
python solve.py
```

`solve.py` hardcodes `DRONE_HOST = 10.13.37.30` — update it if your
environment maps the service differently. Expected output ends with:

```
FLAG → flag{d3t0n4t3_dm7}
```

`modbus`, `device-identification`, `osint`, `live-process`

## Setup / Deployment Notes

```bash
VENDOR_URL=http://<challenge-host>:8080 docker compose up -d --build
```

Two services come up on `10.13.37.0/24`:

- `drone` (10.13.37.30) — the DM-7's Modbus/TCP interface, port 502.
- `website` (10.13.37.50) — the AstraTech marketing site, port 80.

On Linux, the Docker bridge is host-routable, so contestants can reach
both IPs directly. On macOS/Windows (Docker Desktop) use the exposed
host ports instead.

**`VENDOR_URL` is required for a real deployment.** It's what the
drone's FC43 response hands back (`src/drone/server.py`) and what the
generated PDF manual's support line says (`src/website/generate_pdf.py`,
baked in at image build time via a Dockerfile `ARG`) — both default to
`http://localhost:8080` for local GM testing, but that only resolves for
someone on the same machine. Set `VENDOR_URL` to wherever the `website`
service is actually reachable from a contestant (a mapped host port
behind whatever hostname/IP the venue hands out) before bringing this up
for real; the drone's internal bridge IP (`10.13.37.50`) is never
reachable from outside the container network, so it must never be the
value contestants end up needing.

The EDP can only be armed once per server process (`_flag_unlocked`
guards against re-triggering, though re-arming is harmless/idempotent).
To fully reset between contestants: `docker compose restart drone`.

Give contestants only the challenge host and port 502 for the drone —
nothing else needs to be handed out, since the vendor website and its
manuals are discoverable in-band via the FC43 vendor URL, which is the
point. Do not give them `src/drone/server.py` or
`src/website/generate_pdf.py` source.

**Multi-team deployment is still an open question.** As built, `drone`
is one shared Modbus server for everyone — the first team to arm the EDP
permanently populates the flag registers (they're never cleared without
a restart, and reading them back has no auth check), so every team after
the first can skip straight to reading registers 2000–2017 and bypass
the FC43/vendor-hunt puzzle entirely. Tungsten Rain hit the same class of
problem and solved it with a documented per-team-container model
(`challenges/rev/Tungsten_Rain/src/deploy/DEPLOYMENT.md`)
— this challenge needs an equivalent decision (per-team `drone` instance
on a distinct port, most likely, mirroring that pattern) before it's
safe to run with more than one team.

## Known Issues / Notes

- **Multi-team deployment is unresolved (blocking for a >1-team run).** The
  `drone` service is a single shared Modbus server with no per-read auth and
  no automatic reset, so the first team to arm the EDP leaves registers
  2000–2017 populated for everyone else — later teams can skip the entire
  FC43 / vendor-hunt puzzle and just read the flag back. See the
  "Multi-team deployment is still an open question" paragraph under
  **Setup / Deployment Notes** above for the fix direction (per-team
  `drone` instance, mirroring `challenges/rev/Tungsten_Rain/src/deploy/DEPLOYMENT.md`).
  A single-team run, or `docker compose restart drone` between teams, is
  fine in the meantime.
